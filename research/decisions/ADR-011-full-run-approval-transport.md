# ADR-011 — Full run 승인을 붙여넣기 토큰으로도 받고, 파일 승인에 만료를 넣는다

## Status
Accepted (2026-09-22, 사용자 검토) — 코드는 `6179078`에 포함되어 있다.

## Context

ADR-005가 정한 full run 승인은 파일 하나다. 사람이 자기 터미널에서 `scripts/approve_full_run.py`를 돌리면 `experiments/approvals/<exp_id>.<science12>.json`이 생기고, 게이트가 그것을 보고 통과시킨다. Claude Code는 이 스크립트도 이 디렉터리도 거부된다.

사용자가 이 방식이 "위험해서" 다른 형태도 검토해 달라고 요청했다. 실제로 약점이 하나 있다: **이 파일에는 만료가 없다.** 3월에 승인한 실험은 6월에도 같은 파일로 승인된 채이고, 화면 어디에도 그렇게 적혀 있지 않다. `science_hash`에 묶여 있으니 *다른* 실험이 승인되는 일은 없지만, "그때 한 번 봐줬다"가 "계속 봐준다"로 조용히 바뀐다.

여기서 한 가지를 분명히 해야 한다. **이 샌드박스에서 Claude는 사용자와 같은 OS 계정으로 돈다.** 따라서 파일 승인이든 토큰 승인이든, 실제 강제력은 파일 권한이 아니라 `permissions.deny` + hook이라는 **정책**에서 나온다. 어떤 전송 방식도 이 사실을 바꾸지 않는다. 그러므로 "더 안전한 형태"를 고를 때 기준은 *비밀 유지*가 될 수 없고, **승인의 범위와 유효 기간을 얼마나 좁히는가**가 되어야 한다.

## Decision

### 1. 파일 승인에 만료를 넣는다 (기본 24시간)

`ApprovalToken.expires_at`을 추가한다. `--ttl-hours`로 조정하고, `--no-expiry`로 이전 동작(무기한)을 복원할 수 있다. 필드가 없는 **기존 파일은 그대로 유효**하다(하위 호환).

만료 시각을 해석할 수 없으면 **만료된 것으로 취급**한다. 파일이 깨졌을 때 "만료 없음"으로 읽으면 손상된 파일이 영구 승인이 되어 버린다.

### 2. 붙여넣기 형태를 추가한다

```bash
python scripts/approve_full_run.py --init-key          # 최초 1회, 서명 키 생성
python scripts/approve_full_run.py --exp NAME --print  # 파일을 쓰지 않고 토큰을 출력
export PAD_APPROVAL_TOKEN=pad1....                     # 실행할 셸에서
uv run --no-sync python scripts/train.py +exp=NAME
```

토큰은 `pad1.<payload>.<HMAC-SHA256>`이고 payload에 `experiment_id`, `science_hash`, `git_sha`, `approved_by`, `expires_at`이 들어간다. 기본 유효 기간은 **2시간**. 서명 키는 저장소 **바깥**(`~/.config/pad_research/approval_key`, 0600)에 두고, Claude는 이 파일을 건드리는 모든 명령이 hook 규칙 **DG-15**로 거부된다.

### 3. 게이트는 두 형태를 같게 취급하되, 어느 쪽인지 기록한다

`resolve_approval()`이 파일 → 환경변수 순으로 확인하고, run에는 `approved_by`가 `file:<user>` 또는 `paste:<user>`로 남는다. "예전에 받아 둔 승인"과 "이번 실행을 위해 방금 붙여넣은 승인"은 결과의 provenance로서 서로 다른 사실이다.

### 4. 검증 실패는 전부 "승인 없음"으로 수렴한다

위조된 서명, 만료, 다른 실험, 오타, 빈 문자열 — 무엇이든 `None`을 반환한다. 이 코드는 게이트 안에서 돌고, 게이트에게 필요한 답은 오직 "승인이 있는가"다. 여기서 예외를 던지면 게이트가 *잘못된 이유로* 실패할 수 있다.

## Alternatives Considered

- **단회용(single-use) 토큰**: nonce 원장을 두고 한 번 쓰면 폐기. 기각. 게이트는 한 번의 실행에서 여러 번 평가된다(hook의 `validate_spec --for-launch`, 그다음 in-process 게이트). 어디서 "소비"할지 정하는 순간 부분 소비 상태가 생긴다. 그리고 막히는 것은 *같은 실험의 재실행*뿐인데, 그건 GPU 낭비이지 보안 사고가 아니다. 진짜 위험한 경우(다른 실험 실행)는 이미 `science_hash` 결합이 막는다.
- **공개키 서명(사용자 개인키로 서명, 저장소에 공개키)**: 검증이 키 없이 가능해 더 깔끔하다. 기각 이유는 운영 부담 대비 이득이 없다는 것 — 검증도 승인도 같은 머신에서 일어나므로 대칭키로 충분하다.
- **TOTP / 6자리 코드**: 사람이 옮기기 쉽지만 `science_hash`를 담을 수 없다. 그러면 "승인이 정확히 무엇을 승인했는가"가 사라진다. 이 프로젝트에서 그 결합은 협상 대상이 아니다.
- **파일 승인을 없애고 토큰만 남기기**: 기각. 파일 쪽이 무인 실행(큐가 빌 때까지 기다렸다 도는 경우)에 더 적합하고, 이미 ADR-005로 문서화되어 있다. 둘은 서로 다른 작업 방식에 맞는다.

## Why

붙여넣기 토큰이 파일보다 "더 안전"한 지점은 **비밀성이 아니라 시간**이다. 토큰은 셸을 닫으면 사라지고 2시간 뒤 만료된다. 파일은 누군가 지울 때까지 남는다. 사용자가 느낀 위험이 정확히 이 지점이라고 판단했고, 그래서 파일 쪽에도 만료를 넣었다 — 요청받은 것은 새 형태였지만, 문제의 뿌리는 두 형태 모두에 있었다.

또 하나. 토큰을 Claude가 실행하는 명령에 붙여넣으면 **그 토큰은 유효한 동안 Claude에게 보인다.** 이것을 숨기지 않고 코드 docstring과 스크립트 `--help`에 적어 두었다. 승인 체계의 가치는 "Claude가 모른다"가 아니라 "사람이 한 번 봤다 + 그 승인이 좁다"에 있기 때문이다. 전자를 주장하면 거짓이 되고, 거짓인 보안 주장은 없는 것보다 나쁘다.

## Risks

- **재생(replay)**: 유효 기간 안에는 같은 실험을 다시 승인할 수 있다. 의도적으로 허용한다(위의 단회용 항목 참조). 영향은 GPU 시간이고, 실험 내용은 사람이 승인한 그것 그대로다.
- **키 유출**: 키를 읽을 수 있으면 모든 실험의 승인을 만들 수 있다. 완화: 0600, 저장소 바깥, hook DG-15, `permissions.deny`. 이 중 마지막 두 개는 **정책**이며 OS 수준 강제가 아니다 — 위 Context에서 밝힌 대로다.
- **2시간이 너무 짧거나 김**: freeze → smoke → 큐 대기 → 실행이 2시간을 넘는 환경이 있을 수 있다. `--ttl-minutes`로 조정 가능하고, 넘기면 다시 발급하면 된다.
- **기존 무기한 파일 토큰의 잔존**: 이번 변경 이전에 만들어진 파일은 계속 무기한이다. 의도적이다(하위 호환). 정리하려면 `experiments/approvals/`를 사람이 비우면 된다.

## Evidence

- `tests/unit/test_approvals.py` — 위조 서명, 다른 키, 만료, 다른 실험, 다른 `science_hash`, 파싱 불가능한 만료, 키 파일 권한(0600), 하위 호환(만료 필드 없는 파일).
- `tests/unit/test_gate.py::test_a_pasted_token_approves_the_run_and_is_recorded_as_such` — 붙여넣기 토큰이 게이트를 통과하고 `approved_by`가 `paste:`로 남는다.
- `tests/unit/test_gate.py::test_a_pasted_token_for_another_experiment_does_not_approve_this_one` — 셸에 남아 있는 토큰이 다음 실험을 승인하지 않는다.
- `tests/hooks/test_guard_destructive.py` — 서명 키를 읽기/복사/출력/덮어쓰기 하는 명령과 환경변수로 우회하는 명령이 모두 DG-15로 거부되고, 무관한 ssh 키 작업은 통과한다.
